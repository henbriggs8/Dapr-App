Then implement the smallest safe backend foundation for:

1. Verification submission

When an application is in `verification_requested`, the provider needs to be able to submit the requested verification information/documents.

Create a native-safe endpoint such as:

POST /api/provider-applications/me/verification

Auth:
Authorization: Bearer <clerk_token>

The endpoint should:

* verify the authenticated user owns the application
* only allow submission when status is `verification_requested`
* save verification metadata/document references safely
* transition the application to `verification_submitted`
* never expose private verification data through public/provider-facing responses unnecessarily

Do not invent a new file-storage architecture if one already exists. Inspect first and reuse the safest existing pattern. If there is no appropriate document-storage system, stop and explain the recommended approach before implementing storage.

2. Provider setup

Once an application reaches `approved_needs_setup`, the native app needs a setup flow before activation.

Create or extend backend storage for provider setup fields such as:

* profile/display name
* profile photo reference if supported
* phone
* service area / ZIP codes
* availability
* vehicle/equipment readiness
* payout onboarding status
* required agreement acceptance timestamps

Do not overbuild scheduling or dispatch logic here. This phase should only store the minimum information required to determine whether a provider is ready for activation.

Create native-safe endpoints for:

* GET current setup state
* PATCH/save setup progress

For example:

GET /api/provider-setup/me
PATCH /api/provider-setup/me

Return explicit completion flags so SwiftUI does not need to recreate backend business logic.

Example shape:

{
"setupComplete": false,
"requirements": {
"profileComplete": true,
"serviceAreaComplete": true,
"availabilityComplete": false,
"payoutSetupComplete": false,
"agreementsComplete": true
}
}

Use the actual existing backend conventions rather than blindly copying this shape.

3. Stripe Connect

We eventually need providers to receive payouts through Stripe Connect.

Do NOT replace or interfere with the existing customer Stripe payment flow.

If Stripe Connect is not currently implemented, build only the safe backend foundation needed to:

Keep all Stripe secret operations server-side.

Do not mark payout setup complete simply because an account exists. Use Stripe's actual readiness/account status.

4. Provider activation

Create a server-side activation check.

A provider may transition:

approved_needs_setup → active_provider

ONLY when all required setup conditions are satisfied.

Activation should happen through backend-controlled completion logic, not an admin status button and not a value sent by the Swift app.

When activation succeeds:

* application status becomes `active_provider`
* the appropriate user/provider flag such as `users.isProvider` is set
* changes occur atomically if possible
* repeated activation calls are idempotent

Do not change the meaning of existing `users.isProvider` fields without inspecting their current usage first.

5. Preserve the existing status endpoint

canBeginProviderSetup
isActiveProvider

You may safely add fields if useful, but do not rename/remove existing ones.

* enforce status/state transitions server-side
* avoid returning sensitive verification information
* use existing API error conventions
* maintain TypeScript correctness
