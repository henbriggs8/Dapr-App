## Part 2 — Add a Booking Payment Completed Event

I want a new event whenever a customer successfully completes payment for a booking.

The event should represent:

`booking.payment_completed`

This must only occur once the backend has authoritative confirmation that Stripe payment succeeded.

DO NOT trigger this based solely on:

* the user reaching a payment success screen
* an iOS callback
* a frontend state change
* a redirect
* the customer closing/reopening the app

Use the existing authoritative backend Stripe/payment verification flow.

Inspect the existing booking/payment architecture and determine the safest location to emit this event.

The payment flow must remain idempotent.

If Stripe, the customer app, or our API retries the request, we must NOT create duplicate bookings, duplicate payment events, or duplicate emails.

## Part 4 — Create Notification/Event Tracking

I don't want Resend emails to be invisible side effects.

I want us to be able to track exactly what notifications have occurred.

First inspect whether we already have a notification log, event log, audit log, email log, or similar database structure.

If one already exists, extend/reuse it instead of unnecessarily creating another system.

If none exists, propose and implement a lightweight table similar to:

`notification_events`

Suggested fields:

* id
* event_type
* booking_id nullable
* user_id nullable
* provider_id nullable
* recipient
* channel (`email`)
* provider (`resend`)
* template / notification_type
* status (`pending`, `sent`, `failed`)
* provider_message_id
* error_message nullable
* metadata JSON
* idempotency_key
* created_at
* sent_at
* failed_at

Use the project's existing naming conventions and database architecture rather than blindly copying those field names.

For the paid booking notification, create a deterministic idempotency key such as:

`booking.payment_completed:{booking_id}:admin`

or another equivalent reliable key.

There should only ever be one successful internal notification for the same booking/payment event unless we intentionally resend it.

## Part 5 — Logging and Error Handling

An email failure must NEVER cause a successful customer payment or booking confirmation to fail.

Payment/booking completion is the primary transaction.

Email is a secondary side effect.

If Resend fails:

* preserve the successful booking/payment
* record the notification as failed
* log the error
* make the failure observable
* do not return an incorrect payment failure to the customer

Use the existing logging infrastructure where possible.
