I want to build the production provider application system for Become a Dapr Pro.

This is different from our recent website-only redesign work.

This feature intentionally requires new backend functionality because the provider application needs to become the single source of truth shared by the Dapr website and the separate native SwiftUI Dapr Pro app.

Core architecture

The provider application record must live in the existing Replit backend/database.

The website and native SwiftUI provider app should both consume that same backend record.

The desired future flow is:

Dapr website
→ /providers/apply
→ applicant submits application

Shared backend
→ stores one canonical provider application

Admin
→ reviews application
→ changes application status
→ requests verification if appropriate
→ approves/rejects applicant

Native Dapr Pro app
→ applicant signs in
→ backend identifies their existing application
→ app displays their current status
→ approved applicants continue provider account/setup
→ applicant does NOT submit another application

Do not create a website-only provider application system that the native app cannot consume.

Why I prefer this over Codex's original prompt

Codex designed a very good finished system.

But the original prompt jumps immediately from:

“What's your name?”

to:

private driver's-license storage + signed URLs + video uploads + file metadata + admin verification infrastructure

That's a lot of complexity before you've had applicant #1.

And I think your actual provider funnel should eventually look like:

Dapr.com
→ Become a Pro
→ Apply
→ Dapr reviews

Then only people you actually want:

→ Verification requested
→ license + vehicle verification
→ Approved
→ download/open Dapr Pro app
→ finish account setup
→ training
→ go online
