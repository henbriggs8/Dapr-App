Schema review and canonical policy

The existing services table has id, name, description, price, duration and category. It has no service availability/status column. Price and duration are required integers. No schema columns or migration SQL changed. Availability is derived from the existing category, and canonical selection chooses one stable record per tier by ID.

shared/service-catalog.ts is the canonical seed/availability policy. The API adds bookingAvailability, isBookable, customerVisible and displayPrice metadata without changing the six existing service fields. Numeric Black Label legacy/internal values remain for compatibility with historical records and older app decoders; customer UI never displays its price and displayPrice is null. Interior and duplicate service records remain readable, but are not valid new selection/booking targets.

API enforcement and history

  • Native quote creation, Arrive Now availability, quote-to-booking creation and the legacy booking endpoint enforce the same server-side catalog rule.
  • Direct service IDs, crafted client availability flags, stale quotes and hidden duplicate IDs cannot create new Interior or Black Label bookings or bypass the canonical selection.
  • Rejected quote consumption occurs before slot capacity, referral debits, quote consumption or booking writes.
  • Existing bookings remain readable and idempotent. Existing paid booking lifecycle, dispatch, provider history and finalized earnings are preserved.
  • Catalog initialization no longer deletes duplicate service rows or repoints historical bookings. Interior rows are left untouched.
  • The 65% Provider / 35% Dapr compensation model and Dapr-funded discounts remain unchanged.

Customer, provider and admin surfaces

The customer iOS app retains its Coming Soon card, uses the full Dapr Black Label Detail name, has no Black Label price/booking action, restores Essential Wash naming, and accepts additive server availability metadata. The complete catalog is retained separately for historical active-booking lookups. Direct booking/deep-link guards reject unavailable services.

Web home pages, desktop/mobile service overview and comparison, booking screen, location booking widget, reusable service selection, pricing slider, booking dialog and rebooking suggestions enforce the two-service policy. The legacy web widgets now use /api/bookings/legacy; the location widget supplies the selected slot date/time and checks availability errors, and rebooking keeps the legacy USD amount unit. Black Label stays visible as Coming Soon. Corporate fleet inquiry estimates remain a separate non-booking inquiry flow; they do not create marketplace bookings.

Admin/provider service lookup retains the original service IDs, required numeric fields and retired records. Provider/admin lifecycle and historical detail paths do not apply new-booking eligibility retroactively. The active provider app uses ProviderRuntime job workflows rather than a customer catalog checkout; no provider iOS code or release configuration was modified.
